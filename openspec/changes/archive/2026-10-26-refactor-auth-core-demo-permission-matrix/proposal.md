# Proposal: refactor-auth-core-demo-permission-matrix

## Why

`sample/auth-core-boot-sample` 的浏览器验证台目前把身份写死在每条用例里：C1 是"alice 编辑工单1"、C2 是"bob 编辑工单1"，同一个场景按人拆成多行；顶部"手工身份"下拉框却只驱动权限回显与自由调用，不驱动矩阵。使用者看到的是一份"按人写的测试清单"，而不是"当前登录态有哪些接口和数据的权限"，既不直观，也无法回答演示场合最常被问的问题——换一个人，他能进哪些接口、能改哪些数据、能看到哪些行。

这与 2026-10-22 `clarify-auth-core-demo-identity-scope` 的"用例身份固定、手工身份仅回显"裁决相反。本轮按新目标调整：主矩阵的身份从"每条用例的夹具"改为"驱动整张矩阵的镜头"；规格断言仍以固定夹具留在 `verify.sh` 与自动化测试中，页面不再承担断言执行。

## What Changes

- **页面语义**：删除场景矩阵的逐用例 `demoUser`；主表改为"一行一个判权场景"，顶部身份下拉框驱动整张主表。切换身份时自动刷新只读判定。
- **期望与一键测试**：主表每行显示当前身份的**期望结果**（页面内固定真值表，25 行 × 7 身份）与**实际结果**，逐条给出通过/不通过/不适用；顶部“测试当前身份”一键重跑并汇总，切换身份自动测试一次。顶部增加“当前身份能做什么（既定）”总览，按可执行 / 接口可进但数据不可操作 / 不可进入 / 可查看的数据 / 看不到的数据 / 不适用分组。
- **分层展示**：每条判权行分别显示菜单层（路径授权）、行级层（业务数据槽位）与数据范围层（可见行集）的结果；展开可看"该路径/槽位要求哪些权限串、当前身份持有哪些权限串"。
- **只读预检**：示例新增只读端点 `/demo/permission-view`，对一批菜单路径与行级槽位调用框架现有的 `AuthMenuHandler.hasMenuAccessAuth` 与 `AuthDataHandler.hasDataOperateAuths`，并返回判定依据；不执行任何业务方法体，不写业务表与副作用表。
- **不执行写操作**：编辑/审批/授权等行只显示判定；每行的"真实调用"只把方法与请求体填入页面底部的"自由调用"面板，由使用者手动发送。切换身份不会写 `demo_execution_log`、不会修改业务数据、不会改变权限槽位。
- **用例合并**：只合并"同一个调用、不同身份"的重复行（C1/C2/C12b → 一行"编辑工单1"；B11/B12 → 一行 `/deptInherit/ledger`），不同接口、不同数据、不同槽位的用例保持独立。每行保留"覆盖原编号"，`verify.sh` 的编号与断言不变。
- **覆盖脚注**：页面主表只承载判权场景；能力场景（用法错误 400、未声明接口、trace 细节、编解码）与规格断言（启动失败、重启、授权翻盘）以可折叠的"覆盖核对"列出，逐条指向 `verify.sh` 断言或测试类，确保没有原编号被丢掉。
- **C22 判据修正**：现有 C22 标称验证"管理动作自身受行级管辖"，但 `/authData/grant` 的菜单授权只给了 `ROLE__10`，bob 在菜单层已被拒，行级切面未执行。种子数据把 `/authData/grant|remove|fill` 的菜单授权补授予 `ROLE__20`，行级槽位 `demo_admin/900/unified` 仍只给 `ROLE__10`，使 bob 能进管理接口但不能操作槽位；`verify.sh` 的 C22 仍断言 403，并可收紧为断言"权限校验不通过"以证明拒绝发生在行级。
- **文档**：README 第 4.1 节改写为"身份驱动权限主矩阵 + 期望/实际/结果 + 一键测试 + 身份能力总览"；第 6 节增加"页面入口/覆盖核对"映射与身份真值表说明，删除"页面用例编号与 `verify.sh` 完全一致"的旧说法，改为"判权期望在页面真值表、副作用/启动/规格断言在脚本/测试"。
- **非目标**：不修改框架代码与框架规格；不改变任何权限判定语义、接口行为、H2/MySQL 数据源与建表约束；不引入第二套权限模型或第二套验证页面。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

无。

本变更只调整示例工具（浏览器验证台）的呈现语义、示例自有的只读观察端点、示例种子数据中的一条菜单授权，以及说明文档；`sample/auth-core-verification-demo` 要求的"文档 + 可执行脚本同源"仍由 README 场景矩阵与 `verify.sh` 满足，框架与示例的规格级行为不变。因此变更元数据以 `skip_specs: true` 显式退出规格增量。

## Impact

- **页面**：`sample/auth-core-boot-sample/src/main/resources/static/index.html`（单视图权限矩阵、分层判定、只读预检、覆盖脚注、自由调用预填）。
- **后端（仅示例）**：`sample/auth-core-boot-sample` 的观察端点新增只读 `/demo/permission-view`（优先放在 `DemoMetaController`，或独立 controller）；不触碰 `../../../../auth` 框架代码。
- **数据（仅示例）**：`sample/auth-core-boot-sample/sql/seed-data.sql` 补授 `/authData/grant|remove|fill` 的 `ROLE__20` 菜单权限；不新增表、不改变主键形态。
- **脚本**：`sample/auth-core-boot-sample/verify.sh` 编号与断言主体不变；C22 可选收紧为断言行级拒绝消息。
- **文档**：`sample/auth-core-boot-sample/README.md` 第 4.1、6 节及相关旧表述。
- **决策取代**：本变更取代 2026-10-22 的"用例身份固定、手工身份仅回显"边界；新边界为"主矩阵身份=镜头，规格断言=脚本/测试的固定夹具，页面不执行写操作"。
- **验证方式**：浏览器人工回归（切换 7 种身份，主表期望/实际/结果与身份能力总览同步；alice/bob/carol/dave/frank/无身份 25/25 通过，erin 16/16 通过 + 9 条不适用；切换身份/一键测试零写请求）；`bash verify.sh` 全量通过；REST 调用 `/demo/permission-view` 与真实接口的放行/拒绝结论一致。
