## 一、自定义 OAuth2 用户服务 `IdaasSPOAuth2UserService`

> 本条结论**据提交记录推断，非作者确认**。该类在 git 全历史中从未作为文件存在过，只在一行被注释掉的代码里被引用过一次，意图无法直接考证。

### 曾试过什么

对接外部 idaas 身份源时，令牌交换成功、用户信息也拿到了，但拿不到业务侧的 `systemUser`。当时的应对是在 `Oauth2Config` 里留一行注释掉的

```java
//return new IdaasSPOAuth2UserService();
```

打算用一个自定义的 `OAuth2UserService` 子类，在加载用户信息时介入，把身份源返回的属性和业务用户表关联起来。

同一次排障还创建了一个配套的 `IdaasSPOAuth2LoginAuthenticationProvider`——把 Spring Security 的 `OAuth2LoginAuthenticationProvider` 包一层，在 `delegate.authenticate()` 返回后取到 `OAuth2User`。它是个空壳，取到主体之后什么都没做，纯粹是为了占一个拦截点。

### 为什么放弃

拦截点选错了位置。在认证器或用户服务里做"身份源属性 → 业务用户"的转换，意味着把业务查询塞进了 Spring Security 的认证链路，认证流程被数据库访问拖住，一旦查不到用户还会以认证异常的形式冒出来，很难和真正的认证失败区分。

### 现在的替代方案

当时改为**Session 里保存认证器返回的最原始数据，等到真正使用 Authentication 的时候再做转换**，这样认证链路本身不被业务逻辑阻塞，转换失败也不影响登录成功。落地在 `Oauth2AuthenticationSuccessResultConverter`。

**这条替代方案本身已在 2026-10-18 被废弃**，本节的"拦截点位置"结论随之反转，理由与新的落点见第六节。原本挂在它上面的引用路径 `qy-idaas/idaas-authentications/.../oauth2/result/` 也早已不存在——那个类后来位于 `login-spring-boot-starter/.../oauth2/result/`，现随转换层一起删除。

本节仍然有效的事实只有一条：那个空壳 `IdaasSPOAuth2LoginAuthenticationProvider` 在方案切换当天就被删除了，`Oauth2Config` 里只有 `//return new IdaasSPOAuth2UserService();` 一行注释活了下来，成了指向一个从未入库的类的墓碑。

## 二、`RestOperationBuilder` 里的 SSL 豁免分支

### 曾试过什么

同一次 idaas 对接排障（`cf642d9`）中，除了上面的用户服务，还新建了 `RestOperationBuilder`，并在 `Oauth2Config` 的调用点写死了

```java
defaultOAuth2UserService.setRestOperations(new RestOperationBuilder().enableSsl(false).build());
```

`enableSsl(false)` 会让构建出的 HttpClient 信任所有证书并跳过主机名校验（`loadTrustMaterial((c,a)->true)` + `NoopHostnameVerifier`）。

### 为什么这条路是错的方向

**当初的故障不是证书故障，是响应解析故障。** 判据有三条：

1. `RestOperationBuilder` 自己的类注释写的是"支持处理非标准格式的 Userinfo 响应（如 HTML 错误页面）"，它真正做的事是替换消息转换器（`StringHttpMessageConverter` + `MappingJackson2HttpMessageConverter`）和错误处理器（`OAuth2ErrorResponseErrorHandler`）。
2. 它与 `enableSsl(false)` 出自**同一个提交**，提交说明是"调用通了但是没有systemUser"——数据没拿到，不是连不上。
3. 同提交里 `Oauth2Config` 的注释写"用来解决 Oauth2 默认的 ssl 证书校验"，与该类自己的类注释相互矛盾。两处注释对同一个类的作用给出了不同说法，而调用点的硬编码让措辞不准确的那一处看起来像是设计意图。

也就是说，SSL 豁免是排障时顺手加的 shotgun，真正起作用的是转换器配置。这个硬编码后来变成了全仓唯一的 userinfo 通道，使**所有**引入该 starter 的应用无条件跳过 TLS 校验。

### 现在的替代方案

`RestOperationBuilder` 保留（转换器与错误处理器那部分继续有效）。`enableSsl` 不再由调用点写死，改由配置项 `cu.security.login.oauth2.clients[*].ignore-ssl` 驱动，默认 `false` 即执行证书校验，未配置的注册回落安全实例。

**有意的不对称**：OIDC 端点发现（`ClientRegistrations.fromIssuerLocation`）走 Spring 自带的 `RestTemplate`，始终执行标准证书校验，不受 `ignore-ssl` 影响。discovery 失败发生在启动期且异常信息明确，为它放宽校验的代价远高于收益。

### 验证状态

**运行时未验证。** 去掉 SSL 豁免后，当初报错的那个 idaas 环境是否仍能正常登录，尚未实测（该环境在本次改动时不可访问）。

已验证的部分仅限接线正确性（`Oauth2UserServiceWiringTest`）：默认走证书校验、`ignore-ssl` 只影响被配置的那个客户端、未匹配的 registrationId 落到安全实例。

若后续实测发现该 IDP 确实需要豁免，把对应客户端配成 `ignore-ssl: true` 即可，**不要**把默认值改回不校验。

### 对应提交

| 提交 | 日期 | 说明 |
|---|---|---|
| `cf642d9` | 2026-02-22 | 引入 `RestOperationBuilder` 与 `enableSsl(false)` 硬编码 |

## 三、Header 传递的 Remember-Me：`AbstractHeaderRememberMeServices` 与 `PersistentHeaderRememberMeService`

### 曾试过什么

用 HTTP 响应头而不是 Cookie 传递 remember-me 令牌。`AbstractHeaderRememberMeServices` 实现了 `RememberMeServices` 与 `LogoutHandler`，把 `series` 和 `token` 用逗号拼成一个头（`remember-me-token`）写回响应，登录失败和登出时试图通过 `response.setHeader(name, null)` 清除它。`PersistentHeaderRememberMeService` 是它的唯一实现，配 `PersistentTokenRepository` 做令牌持久化。

### 为什么放弃

两条理由，第一条是设计层面的，作者当时就没想通：

1. **header 模式在这个场景下没有意义。** 用 header 传令牌，意味着每个请求都要由前端主动带上这个头——那和把 token 的有效期直接延长没有区别，反而多了一套签发、拼接、解析的机制。原作者在两个类的注释里都留了同一句话："没考虑明白，rememberMe如果用header传参的话岂不是每个请求都会带上，那就没有意义了，直接把token的时间延长就好了呀"。
2. **被 Spring Session 取代。** 会话持久化改用 Spring Session 之后，token 模式本身也不再需要，这套实现整体失去存在前提。

此外，这两个类还带着两处未修复的实现缺陷。**它们至今仍然存在**，因为类被有意保留（见下节）。在决定真正移除之前，任何复用这两个类的人都会直接继承这两条：

- `response.setHeader(name, null)` 在 Servlet 规范下**不会**移除已有的响应头，"登出时清除令牌头"这个动作从来没生效过。header 类响应头没有删除语义。
- `key` 字段默认值是 `"123456"`，它是 `RememberMeAuthenticationToken` 的构造参数、也是 `RememberMeAuthenticationProvider` 的校验依据。写死默认值意味着任何知道这个框架的人，在开发者忘记调 `setKey()` 时都能伪造 remember-me 认证。`afterPropertiesSet()` 里的 `Assert.hasLength(key, ...)` 只挡空串，挡得住没配，挡不住用默认值。

### 当前状态：保留，但已废弃

**两个类未删除，仍以 `@Deprecated` 形式留在 `qy-auth/auth-spring-boot-starter/.../security/extension/`。** 作者于 2026-10-13 明确决定保留——废弃标记本身已经足够表达态度，不需要靠删除来传达。

因此本节记的是"为什么不要再用这条路"，不是"这条路已经被拆掉"。读的时候按警告看，不要按墓碑看。

### 新的会话保持方案

推荐路径是 Spring Session：`SessionConfig` 注册 `SpringSessionRememberMeServices`，由 `cu.security.remember-me.enabled=true` 开启，令牌有效期走 `cu.security.remember-me.validity-seconds`。这条正是上面第 1 条理由的落地——直接延长 token 时间，不再另造一套 header 令牌。

### 已核验的事实

`PersistentHeaderRememberMeService` 是全仓唯一子类；两个类均无 `@Component`/`@Bean` 注解，`*.factories` 与 `*.imports` 中无登记，除彼此外零引用。即它们当前不参与任何 Bean 装配，保留与否不影响现有应用的启动与运行。

## 四、按数据库方言分多份建表脚本

### 曾试过什么

同一套权限表存了两份 Navicat 导出：`auth_full.sql`（抹掉方言子句的通用版）和 `auth_20240801.sql`（保留 `ENGINE = InnoDB CHARACTER SET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci` 的 MySQL 8.0.36 原样快照），当时按"全量脚本 + 带日期的增量快照"来管理。

脚本散在四处：`qy-auth/relation/sql/`、根目录 `relation/auth.sql`（实际是 0 字节占位）、`../../sample/auth-rbac-boot-sample`（建表和示例数据混在一起）、`sample/basic-boot-sample/src/main/resources/`。文档里引用的 `script/sql/auth.sql` 这类路径，对应的目录从来不存在。

### 为什么放弃

两份只差方言子句，同一张表的改动要同步两遍，而且已经漂了：`sys_request_log` 在 `basic-support.sql` 里仍是 `url` 且缺 `status`，实体 `SysRequestLog` 早就改成 `api_path` + `status`。

方言子句还把脚本锁死在 MySQL 8 上——H2 不认识 `utf8mb4_0900_ai_ci`，也就没法用同一份脚本跑内存库 demo。

### 现在的替代方案

`docs/sql/` 每个域只留一份脚本，只写 MySQL 与 H2(MODE=MySQL) 都接受的语法；字符集、引擎、行格式一律不写，交给各库自己的默认值。方言快照不再保留。

示例专用的建表和种子数据放回各自模块（`sample/*/sql/`）。sample 不再手抄框架 DDL，由 pom 的 `<resources>` 把 `docs/sql` 挂到 `classpath:sql/` 供 `spring.sql.init` 使用。

### 已核验的事实

用 H2 2.1.214 + `MODE=MySQL` 逐条执行得到的兼容结论：

- 接受：内联 `KEY` / `UNIQUE KEY`、`AUTO_INCREMENT`、`json` 列、`ON UPDATE CURRENT_TIMESTAMP`、表级 `COMMENT =`、反引号、`bigint(20)` / `tinyint(1)` 这类带精度的写法（会被归一成 `bigint` / `tinyint`）
- 拒绝：`SET NAMES`、`USING BTREE`
- **索引名作用域不同**：MySQL 是表内唯一，H2 是全库唯一。原来 `sys_user_dept`、`sys_user_role`、`sys_user_credential` 三张表的索引都叫 `user_id`，在 H2 直接冲突，现在统一成 `idx_表名_列` / `uk_表名_列`
- H2 的 `RUNSCRIPT` 会吞掉脚本内部的错误，不能用来做兼容性校验，所以检查器走 JDBC 逐条执行

MySQL 侧未实测（本机没有可连的 MySQL），依据是脚本只使用两边公共子集，改完仍需在自己的 MySQL 上过一遍。

## 五、`RbacResultAdviceHandler` 响应包装切面

### 曾试过什么

`auth-rbac` 有一套自己的响应模型（`RbacResult`、`RbacPageResult`、`RbacPageReq`、`RbacIdReq`、`RbacIdsReq`），与 `basic` 里的 `Result`/`PageResult`/`PageReq`/`IdReq`/`IdsReq` 字段几乎重复，只是分页字段用了 `Long`。为了让两套模型并存时对外仍然是统一格式，`auth-rbac-spring-boot-starter` 里注册了 `RbacResultAdviceHandler`（`ResponseBodyAdvice`），在写出响应前把 `RbacResult` 的 `code`/`message`/`data` 复制进 `Result`。注意它连 `success` 字段都没复制，`Result` 里的 `success` 靠这条切面补全。

### 为什么放弃

1. **两套模型没有第二套的必要。** RBAC 控制器与 sample 控制器已经全部直接用 `basic` 的 `Result`/`PageResult`/`PageReq`/`IdReq`，复制一层只是让同一份数据在两个类之间来回搬。
2. **这条切面本身是坏的。** `supports()` 判断的是 `returnType.getParameterType().isAssignableFrom(RbacResult.class)`，声明返回 `Object` 的接口也会命中，然后 `beforeBodyWrite` 无条件把 body 强转成 `RbacResult`——返回 `List` 的 `Object` 接口会直接 `ClassCastException`。
3. `basic` 侧的异常出口（`GlobalExceptionHandlerAdvice`、`AuthExceptionHandler`）从来就返回 `Result`，不经过这条切面，统一格式并不依赖它。

### 现在的替代方案

控制器直接返回 `com.cu.framework.basic.model.Result`，由 `Result.success()/failed()` 工厂方法一次写全 `code`/`success`/`message`/`data`，不再需要响应期包装。分页字段统一为 `Integer`——分页不存在需要 `long` 的页码与页大小。

随模型一起删除的还有 `RbacResult`、`RbacPageResult`、`RbacPageReq`、`RbacIdReq`、`RbacIdsReq` 五个类；`MybatisPageExecutor` 保留，位置迁到 `basic-support/.../utils/`，它已经只依赖 `basic` 的模型。它与同目录下的 `PageUtil` 功能重叠（后者没有 `Query`/`pageConsumer` 那部分），**尚未合并**。

### 对应提交

| 提交 | 日期 | 说明 |
|---|---|---|
| — | 2026-10-16 | RBAC 模型统一到 `basic`，删除五个 `Rbac*` 模型与该切面 |

## 六、按协议分派的实体转换层 `AuthenticationSuccessResultConverter`

### 曾试过什么

第一节选定的方案：Session 里存认证器返回的最原始主体（`DefaultOAuth2User` / `DefaultOidcUser` / `DefaultSaml2AuthenticatedPrincipal`），等要用的时候再转成本系统的 `SecurityUser`。落地形态是 `AuthenticationSuccessResultConverter` 接口加三个实现（`SecurityUser...`、`Oauth2...`、`Saml...`），由 `ObjectProvider` 注入到两处消费点：`JsonAuthenticationSuccessHandler` 产响应体、`SecurityUserContext` 产当前用户，各自遍历 `support()` 命中第一个。

### 为什么放弃

1. **同一个 `Authentication` 有两条口径不同的转换路径。** 响应体的字段取自身份源声明（OAuth2 甚至从声明里读 `authInfo` 当权限），而 `getCurrentUser()` 回查本地库。同一个用户在接口响应里和权限判定里可能不是同一套数据。
2. **它从未跑通过。** 查库用的是 `principal.getName()`，也就是 `user-name-attribute-name` 指向的值；demo 配的是 `sub`，而本地 IDP 的 `sub` 是数字 ID。于是单点登录成功的响应看起来正常，随后任何 `getCurrentUser()` 都抛 `UsernameNotFoundException`——响应期不查库、消费期才查库，失败被推后到了不相干的地方。
3. **每请求一次库。** SSO 会话每次取当前用户都查库，账密会话却不查。
4. 认证对象的权限集合在 SSO 下是 `OidcUserAuthority` 与 `SCOPE_*`，不是本系统权限码，和 `getCurrentUser()` 拿到的又是两套。

### 现在的替代方案

回到认证链路内转换，并补上当初缺的两块：

- 三种协议的主体在进入 `SecurityContext` 之前就是 `SecurityUser`：`oauth2/Oauth2SecurityUser`（实现 `OidcUser`）与 `saml/SamlSecurityUser`（实现 `Saml2AuthenticatedPrincipal`）。之所以必须分两个子类型而不是一个类实现全部接口：`OAuth2AuthenticatedPrincipal.getAttributes()` 返回 `Map<String, Object>`，`Saml2AuthenticatedPrincipal.getAttributes()` 返回 `Map<String, List<Object>>`，同一个类无法同时满足。
- 装配点：`oauth2/SecurityUserSsoAssembler`（OAuth2/OIDC 共用）、`oauth2/SecurityUserOidcUserService`、`saml/SecurityUserSamlAuthenticationConverter`；账号一律经 `SecurityUserDetailsService` 取，业务要改匹配规则就覆盖那个实现，框架不再提供第二层转换概念。
- 第一节放弃它的两条理由分别由这两条承担：查不到用户时以 `exception/SsoErrorCodes.LOCAL_USER_NOT_FOUND` 的可区分错误码终止认证，不再与真正的认证失败混淆；业务查询从"每请求一次"变成"登录时一次"。
- `SecurityUserContext.getCurrentUser()` 只剩一次 `instanceof` 判定与强转；`LoginSuccessResult` 保留为对外响应体，投影逻辑收进它的静态工厂 `of(SecurityUser)`。

代价：主体在会话里成为登录时快照，改权限需重新登录生效（与账密登录原本一致）。

### 补记（2026-10-19）：装配点为什么必须是三个类，且装配只能发生在链路末端

本轮把 `Oauth2Config` 里两层嵌套的 userinfo lambda 换成具名类时，重新评估过两条"看起来更简洁"的做法，都不成立。理由记在这里，以免下一轮再试一遍。

- **`SecurityUserOidcUserService` 不能继承 OAuth2 侧的用户服务。** Spring Security 5.7.11 里 `OidcUserService implements OAuth2UserService<OidcUserRequest, OidcUser>`，`DefaultOAuth2UserService implements OAuth2UserService<OAuth2UserRequest, OAuth2User>`：同名接口、不同泛型参数，两者互不可赋值，而 `OidcUserService` 是 **组合**一个 `DefaultOAuth2UserService`（经 `setOauth2UserService`）而不是继承它。OIDC 侧必须继承 `OidcUserService` 才保得住 ID Token 校验、nonce 校验与 `sub` 一致性校验，加上 Java 单继承，装配逻辑没有可共享的父类可放。所以 `SsoSecurityUserConverter` 只能作为被两条链路共同持有的第三方存在，删不掉；删它的代价是 `loadLocalUser` 那段在两个类里各写一遍。
- **装配不能下沉到取 userinfo 那一层。** 把装配塞进 per-client 的 userinfo 服务后，OAuth2 链路确实少一层，但 OIDC 链路连坏三处：该实例同时充当 `OidcUserService` 的内部委托，而 `OidcUserService` 只消费委托返回主体的 `getAttributes()` 并自己用 ID Token 重建主体，于是外层装配仍须保留，本地账号库每次登录被查两遍；`LOCAL_USER_NOT_FOUND` 会抢在 ID Token 与 UserInfo 的 `sub` 一致性校验之前抛出，失败原因被抛出顺序掩盖；`OidcUserService.shouldRetrieveUserInfo` 为假时（userinfo URI 为空，或 access token 的 scope 不含 profile/email/address/phone）userinfo 请求根本不发出，内层装配一次也不会执行，外层装配仍是必需的。结论：装配 MUST 发生在各协议链路的末端、各一次。

本轮之后的落点：`oauth2/RoutingOAuth2UserService` 按 `registrationId` 分发 userinfo 请求，只发请求不换主体，同时供 OAuth2 端点与 OIDC 内部委托复用；`oauth2/SecurityUserOAuth2UserService` 在其结果上加一次装配，供 OAuth2 端点使用且**不注册为 Bean**（容器里 `OAuth2UserService` 类型的实例保持只有那个只路由的）；`oauth2/SecurityUserOidcUserService` 沿用父类校验并在外层装配；`oauth2/SecurityUserSsoAssembler.assemble(OAuth2User)` 由原来的 OAuth2/OIDC 两个重载合并为单方法，`OidcUser` 是 `OAuth2User` 的子类型，ID Token 与 UserInfo 用一次 `instanceof` 取出。
